## 1. 프로젝트 정의

### 해결하려는 문제

마케팅·기획 직무를 준비하면서 매일 여러 매체를 돌아다니며 브랜드·업계 뉴스를 확인해야 했다. 관심 있는 기업(예: LG전자, 삼성전자 등)의 소식은 특히 놓치기 쉬웠고, 기사 하나하나를 열어 읽기엔 시간이 많이 들었다.

즉 "매일 확인해야 할 뉴스는 많은데, 훑어보는 데 드는 시간을 줄이고 싶다"는 것이 문제였다.

### 대상 사용자

마케팅·기획 직무 취업 준비생(본인). 관심기업의 동향과 브랜드·업계 트렌드를 매일 파악하되, 원문을 다 읽지 않고도 "무슨 일이 있었는지"와 "왜 눈여겨볼 만한지"를 먼저 감 잡고 싶어 한다.

### 왜 이 구조인가

뉴스 개수가 매일 15~20건 안팎으로 많지 않다. 복잡한 추천 시스템보다, 정해진 카테고리와 관심기업 키워드로 매일 같은 시간에 걸러 모아주는 것으로 충분했다. 그리고 기사 제목만으로는 내용을 판단하기 어려운 경우가 많아, 한 줄 이상의 쉬운 설명이 필요했다.

이건 규칙만으로는 부족하고, 요약을 만드는 부분엔 AI가 필요했다.

### 기대 결과

- 매일 아침 들어가면 그날의 관심기업·브랜드·업계 뉴스가 카테고리별로 정리되어 있다
- 기사마다 "무슨 내용인가요?" 한 줄 설명이 붙어 있어 원문을 안 열어도 감이 잡힌다
- 나중에 다시 보고 싶은 기사는 저장해뒀다가 모아볼 수 있다

## 2. MVP 범위

### 핵심 기능

| # | 기능 | 완결 조건 |
|---|---|---|
| 1 | 뉴스 자동 수집 | Google 뉴스 RSS로 관심기업·카테고리별 최근 24~48시간 기사 수집 |
| 2 | 기사 요약 | 원문 본문을 가져와 한 줄 설명 생성 (실패 시 규칙 기반으로 자동 대체) |
| 3 | 카테고리·관심기업 분류 | 브랜드·캠페인 / 소비자·트렌드 / 업계·비즈니스 + 관심기업 워치리스트 |
| 4 | 매일 자동 발행 | GitHub Actions로 매일 자동 실행 → GitHub Pages 자동 배포 |
| 5 | 기사 저장 | 브라우저에 기사를 저장해두고 별도 페이지에서 모아보기 |

### 확장 기능

핵심 기능이 자리잡은 뒤 추가한 것들이다.

- **저장한 기사 모아보기** — 카드의 ☆ 버튼으로 저장, 발행일과 함께 별도 페이지에서 확인
- **아카이브** — 지난 브리핑을 날짜별로 전체 열람

## 3. 기술 스택과 선택 이유

| 영역 | 선택 | 이유 |
|---|---|---|
| 수집 | Python + feedparser | Google 뉴스 RSS 검색을 안정적으로 파싱. 개별 언론사 RSS는 주소가 자주 바뀌어 제외 |
| 요약 | Claude API (실패 시 규칙 기반 대체) | 기사 본문을 쉬운 한두 문장으로 풀어써야 하는데, 이건 규칙만으로는 한계가 있었다. 다만 API 실패(크레딧 부족 등) 상황에도 사이트가 멈추지 않도록 폴백을 넣었다 |
| 템플릿 | Jinja2 | 카테고리·기사 카드처럼 반복되는 구조를 템플릿 하나(`_article_card.html`)로 재사용 |
| 저장 기능 | 브라우저 localStorage | 로그인 없는 개인 프로젝트라, 서버나 DB 없이 그 브라우저 안에서만 저장되는 가장 단순한 방식을 택했다 |
| 배포 | GitHub Pages + GitHub Actions | 별도 서버 비용 없이 정적 사이트를 무료로 자동 배포할 수 있다 |

## 4. 폴더 구조

```
business-briefing/
├── .github/workflows/
│   └── daily-briefing.yml     # 매일 자동 실행 (수집 → 요약 → 사이트 생성 → 배포)
├── config/
│   ├── categories.json        # 카테고리별 검색어·색상·이모지 설정
│   ├── companies.json         # 관심기업 워치리스트
│   └── major_outlets.json     # 신뢰 언론사 목록
├── data/
│   ├── raw_articles.json      # 수집된 원본 기사
│   ├── articles_enriched.json # 본문 추출 + 요약이 붙은 기사
│   └── history.json           # 브리핑 발행 이력
├── scripts/
│   ├── fetch_news.py          # 뉴스 수집
│   ├── fetch_content.py       # 원문 본문 추출
│   ├── summarize.py           # 기사 요약 생성
│   ├── build_site.py          # docs/ 정적 사이트 조립
│   └── common.py              # 공용 유틸 (설정 로드, 랭킹, 중복 제거 등)
├── templates/                 # Jinja2 템플릿 (index/briefing/archive/saved/카드)
├── static/
│   ├── style.css
│   └── saved.js                # 기사 저장/조회 기능 (localStorage)
└── docs/                       # GitHub Pages로 배포되는 실제 사이트 (자동 생성)
```

## 5. 화면 구성

| 경로 | 화면 | 설명 |
|---|---|---|
| `/` | 홈 | 오늘 브리핑 바로가기 + 최근 업데이트 목록 |
| `/briefing/YYYY-MM-DD.html` | 그날의 브리핑 | 관심기업 + 카테고리별 기사 카드 |
| `/archive/` | 지난 브리핑 전체보기 | 발행 이력 전체 목록 |
| `/saved.html` | 저장한 기사 | 브라우저에 저장해둔 기사 모아보기 (발행일 표시) |

## 6. 개발 과정에서 만난 문제와 해결

### 문제 1. AI 요약 API가 크레딧 부족으로 실패

초기에는 API 크레딧이 없는 상태로 배포해 요약 생성 단계에서 계속 실패했다. `400 Bad Request` 로그를 그대로 두지 않고, 에러 응답 본문을 로그에 출력하도록 고쳐서 원인이 "코드 문제"가 아니라 "결제 크레딧 부족"이라는 걸 정확히 짚어낼 수 있었다.

**배운 것** — API 연동에서 에러가 나면, 상태 코드만 보고 넘기지 말고 응답 본문(body)까지 로그에 남겨야 진짜 원인을 알 수 있다.

### 문제 2. 특정 카테고리가 한 매체로 쏠림

"소비자 트렌드" 카테고리가 특정 매체 기사로만 채워지는 현상이 있었다. 원인은 검색 키워드가 그 매체의 제목 표현과 우연히 일치했기 때문이었다.

**해결** — 카테고리당 검색 키워드를 여러 개로 늘려 특정 표현에만 의존하지 않도록 분산시켰다.

### 문제 3. 저장 기능 추가 시 파일 경로 실수

새 기능을 추가하며 파일을 여러 개(`templates/saved.html`, `static/saved.js` 등) 새로 만드는 과정에서, 파일명에 위치 안내용 접두사가 그대로 붙어 저장소 루트에 잘못 생성되거나, 두 파일의 내용이 서로 뒤바뀌어 들어가는 실수가 반복됐다.

**해결** — 파일마다 "어디에 들어갈 파일인지"와 "내용 시작 부분이 무엇인지"(HTML은 `<!DOCTYPE html>`로 시작, JS는 `(function () {`로 시작)를 명확히 구분해 확인하는 절차를 거쳤다.

**배운 것** — 여러 파일을 한 번에 만들 때는, 파일명과 내용이 뒤섞이지 않도록 하나씩 완성본 그대로 대조 확인하는 게 결국 더 빠르다.

## 7. 설계 원칙 — 최소한의 개인정보

- 저장 기능은 서버나 DB 없이 브라우저 localStorage에만 저장한다. 다른 기기·브라우저에는 공유되지 않는다
- 로그인 시스템이 없다 — 개인용 사이트라 계정 정보를 아예 다루지 않는다

## 8. 시작하기

### 사전 준비

- Python 3.11 이상
- (선택) Claude API 키 — 없어도 규칙 기반 요약으로 자동 대체되어 동작한다

### 설치와 실행

```bash
git clone https://github.com/본인아이디/business-briefing.git
cd business-briefing
pip install -r requirements.txt

export ANTHROPIC_API_KEY=본인의_API_키   # 선택

python scripts/fetch_news.py
python scripts/fetch_content.py
python scripts/summarize.py
python scripts/build_site.py
```

### 배포

GitHub Actions가 매일 자동으로 위 과정을 실행하고, 결과를 `docs/`에 커밋해 GitHub Pages가 서빙한다. 수동으로 바로 실행해보고 싶다면 저장소의 **Actions 탭 → Run workflow**를 누르면 된다.
